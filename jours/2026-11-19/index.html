Mise à jour : NSA Net, deuxième jour de perturbations, une maintenance PHP évoquée

Mise à jour du 18 novembre : Les perturbations durent depuis deux jours ; une source confirme une cause liée à une maintenance PHP, et les responsables américains écartent une attaque coordonnée.

nginx2root : CVE-2026-123007, exécution de code via HTTP/2, corrigée en 1.31.9 et 1.30.7

Une faille du support HTTP/2 de NGINX, CVE-2026-123007 (« nginx2root »), est présente depuis la version 1.9.5 de septembre 2015. Elle permet à un attaquant non authentifié d'exécuter du code sur un serveur où HTTP/2 est activé. F5 précise que cela suppose un ASLR désactivé ou contournable ; Wiz affirme l'avoir contourné en test. Le code obtient les droits d'un worker NGINX. Xint a obtenu root via un autre bug du noyau Linux (SCTP), même depuis un conteneur Docker. Quatre autres failles sont corrigées en même temps (CVE-2026-123633, CVE-2026-123634, CVE-2026-121810, CVE-2026-113425), toutes notées 9,2 en CVSS 4.0. Les versions corrigées sont 1.31.9 et 1.30.7 ; NGINX Plus 37.3.0.1 et 37.0.8.1, sans correctif listé pour R34 à R36. Un PoC public existe sur GitHub. Aucune exploitation n'est signalée et la faille n'est pas dans le KEV. Ubuntu et Debian n'avaient pas encore de paquets corrigés. Il faut redémarrer NGINX complètement, un simple reload ne suffit pas.

Pourquoi c'est important

Presque toute infrastructure web ou Ingress repose sur NGINX. Vérifiez si HTTP/2 est actif sur l'origine (openssl s_client -alpn h2), mettez à jour et redémarrez. En attendant, désactiver HTTP/2 bloque deux des cinq failles seulement. Comparez la version complète du paquet avec l'avis de votre distribution.

Microsoft Agent Framework : deux versions PyPI malveillantes volent des identifiants cloud

Des attaquants ont compromis le paquet PyPI officiel de Microsoft Agent Framework, environ 200 000 téléchargements mensuels. Les versions 1.26.1 et 1.26.2, publiées le 17 novembre 2026, embarquent un voleur d'identifiants lancé au démarrage de Python, même sans import du paquet. Il collecte variables d'environnement, fichiers de configuration et processus, visant Azure, AWS, GitHub, Docker, Hugging Face, OpenAI et d'autres. Il tente aussi d'obtenir des jetons d'identité managée Azure et OIDC Azure DevOps ; la 1.26.2 ajoute les jetons OIDC de GitHub Actions. Les données partent vers un endpoint webhook contrôlé par l'attaquant. PyPI a mis en quarantaine la première version, mais l'attaquant en a publié une seconde environ 2,5 minutes plus tard, elle aussi mise en quarantaine. On ignore comment l'accès de publication a été obtenu ; Microsoft n'avait pas répondu à BleepingComputer.

Pourquoi c'est important

Si un poste ou un runner CI a installé 1.26.1 ou 1.26.2, isolez-le, reconstruisez depuis un environnement sain avec la 1.26.0 et faites tourner tous les secrets accessibles. Cherchez le chemin du webhook dans les logs de sortie. Épinglez les versions et hashes de vos dépendances.

Apache Roller : CVE-2026-129448 (CVSS 9.8) exploitée, désérialisation XML-RPC sans authentification

L'Apache Software Foundation indique qu'une faille d'Apache Roller, plateforme de blog Java, est activement exploitée. CVE-2026-129448 (CVSS 9.8) est une désérialisation de données non fiables dans l'endpoint XML-RPC, qui permet à un attaquant distant non authentifié d'exécuter du code. Les versions 4.0.0 à 6.1.4 sont touchées. Le endpoint désérialise les types d'extension fournisseur avant d'authentifier la requête. L'ASF précise que c'est la même faille que CVE-2026-82384, corrigée en septembre 2026 mais qui ne listait que la 6.1.5 comme affectée. Elle ne donne aucun détail sur l'exploitation ni sur les cibles. Le correctif est Roller 6.1.6 ou plus, qui désactive les types d'extension. Contournement : mettre enabledForExtensions à false dans WEB-INF/web.xml, ou retirer le mapping du servlet /roller-services/xmlrpc, puis redémarrer. Désactiver XML-RPC dans l'interface d'administration ne suffit pas.

Pourquoi c'est important

Si vous auto-hébergez Roller, passez en 6.1.6 sans attendre, l'exploitation étant déjà en cours. Sinon appliquez le contournement dans web.xml et redémarrez. Le cas rappelle qu'un correctif de septembre pouvait être incomplet : vérifiez la version réellement déployée.

Mise à jour : Java4Shell, correctifs publiés, conditions d'exploitation et reproductions partielles

Mise à jour du 18 novembre : Les correctifs Oracle et Corretto sont publiés, Red Hat attend encore les siens, et des sociétés de sécurité ont reproduit la corruption mémoire sans exécution de code universelle.

Calif a divulgué Java4Shell (CVE-2026-114938), qui touche OpenJDK depuis la 17.0.6. La faille dépend du décodeur Base64 accéléré par AVX-512 VBMI. Conditions : processeur compatible (Intel Ice Lake et suivants, AMD Zen 4 à Zen 6), JVM sans -XX:UseAVX=2 ou inférieur, et application décodant du Base64 fourni par l'attaquant. ARM64 ainsi que Java 8 et 11 standard ne sont pas concernés, mais toutes les distributions dérivées d'OpenJDK le sont. Oracle a publié les versions 17.0.21.1, 21.0.13.1, 25.0.5.1 et 27.0.1.1. Amazon fournit les builds Corretto correspondants. Red Hat indique que les mises à jour d'EL 8, 9 et 10 ne sont pas encore disponibles. Calif affirme avoir exécuté du code sur Keycloak, Jira, Confluence, Artifactory, Jenkins et PingFederate sans identifiant. Upwind et Blackpoint n'ont reproduit que la corruption mémoire, et Blackpoint dit qu'il n'existe pas de méthode d'exploitation universelle. Les scores divergent : 8,1 (CVSS 3.1) chez Oracle, 9,2 (CVSS 4.0) chez Calif.

Pourquoi c'est important

Inventoriez les JVM, y compris celles embarquées dans Jenkins, Jira ou Keycloak. Mettez à jour dès que le correctif existe pour votre distribution. En attendant, -XX:UseAVX=2 est la mesure d'atténuation citée dans les conditions. Les exploits restent privés, mais des équipes de sécurité reproduisent déjà la corruption mémoire.

PHP : correctifs de sécurité critiques annoncés pour le 19 novembre, toutes versions touchées

Les mainteneurs de PHP ont annoncé une publication de sécurité le 19 novembre 2026 entre 14 h et 14 h 30 UTC, dans le cycle régulier de quatre semaines. Elle corrige des failles touchant toutes les versions supportées, la gravité maximale étant « CRITICAL ». Le projet précise que les failles critiques exigent une configuration non par défaut ou des montages peu courants, sans autre détail. Selon The Hacker News, la publication devrait inclure CVE-2026-115560, une exécution de code à distance. Elle exige qu'une application règle session.serialize_handler sur php_binary ou php_serialize, puis le repasse à php avec ini_set() avant session_start(), avec l'upload progress de session activé, ce qui est le défaut. Mesure conseillée : session.upload_progress.enabled=0 puis redémarrage des workers PHP. Le même article rappelle que PHP2Shell (CVE-2026-109618 et CVE-2026-109619) subit une exploitation limitée.

Pourquoi c'est important

Préparez la mise à jour PHP du jour sur vos images et serveurs. Si votre code change le handler de session avec ini_set(), désactivez dès maintenant l'upload progress de session. Surveillez aussi les images Docker et paquets de distribution, qui arrivent souvent avec un décalage.

Incus avant 7.6.0 : CVE-2026-130778 (CVSS 10.0), contournement d'authentification par certificat

La NVD publie CVE-2026-130778 (CVSS 10.0) pour Incus avant la version 7.6.0. Un attaquant distant peut s'authentifier comme n'importe quel certificat de confiance en ajoutant ce certificat public à la chaîne client TLS qu'il présente. En ajoutant le certificat du serveur ou d'un membre du cluster, il obtient un accès au niveau du cluster. Il peut aussi contourner l'autorisation, modifier le magasin de confiance et influencer les décisions d'autorisation par scriptlet. Seul ce résumé de la NVD est disponible.

Pourquoi c'est important

Si vous exploitez Incus, y compris en cluster et avec l'API exposée sur le réseau, passez en 7.6.0 rapidement. En attendant, limitez l'accès réseau à l'API. Après mise à jour, contrôlez le magasin de confiance à la recherche d'entrées inattendues.

LiteLLM : CVE-2026-40217 exploitée, exécution de code via /guardrails/test_custom_code

La CISA a ajouté CVE-2026-40217 à son catalogue des vulnérabilités exploitées. Elle touche BerriAI LiteLLM : un canal alternatif non protégé permet à des attaquants distants d'exécuter du code arbitraire par réécriture de bytecode via l'URI /guardrails/test_custom_code. Seul un résumé de l'entrée du catalogue est disponible, sans version corrigée ni détail sur les attaques.

Pourquoi c'est important

LiteLLM sert souvent de passerelle vers des API de modèles et détient des clés d'API. Si vous en hébergez une, consultez l'avis éditeur, mettez à jour et n'exposez pas cet endpoint. Faites tourner les clés si l'instance était accessible depuis Internet.

Chargemap : données de comptes extraites via une ancienne interface technique

Chargemap, service de planification d'itinéraires pour véhicules électriques et pass de paiement des recharges, a prévenu ses utilisateurs mercredi 18 novembre. Le 8 novembre 2026, une personne extérieure a exploité une faille sur une ancienne interface technique pour extraire des données de comptes. L'entreprise a détecté une activité anormale le 10 novembre et corrigé la faille le 12. Sont susceptibles d'être exposés : adresse e-mail, nom d'utilisateur, coordonnées saisies à l'inscription, statut d'abonnement et identifiant de connexion Google, Facebook ou Apple. Une empreinte (hachage) du mot de passe a pu être extraite, aucun mot de passe en clair. Chargemap affirme que coordonnées bancaires, historique de recharges, factures et adresse postale sont épargnés, de même que l'identifiant du badge Pass, sauf pour une vingtaine d'utilisateurs prévenus. Les comptes d'anciens utilisateurs peuvent être concernés. La CNIL a été notifiée le 13 novembre et une plainte est engagée. Le nombre de comptes n'est pas communiqué.

Pourquoi c'est important

Si vous avez un compte Chargemap, changez le mot de passe, ici et partout où il est réutilisé, et méfiez-vous des messages se réclamant du service. Côté exploitation, c'est un rappel : les anciennes interfaces techniques oubliées sont une surface d'attaque à inventorier et à retirer.
