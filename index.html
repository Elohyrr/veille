Nspawn 3.0 : une API Docker Engine pour les conteneurs systemd-nspawn

Nspawn 3.0.0 expose sur l'hôte une API compatible Docker Engine (version 1.51, et jusqu'à 1.24 pour les clients). Le socket est /run/nspawn/api.sock, ouvert par nspawn-api.socket, livré désactivé dans les paquets. Avec DOCKER_HOST pointant dessus, les commandes docker run, exec, cp et rm pilotent des machines nspawn. L'API couvre conteneurs, attach, exec, archive, images, volumes et réseaux. Le GitLab Runner avec l'executor docker peut y exécuter ses jobs via le paramètre host. Les droits passent par polkit : root peut tout faire, les autres utilisateurs ont besoin d'une règle, et un utilisateur avec org.nspawn.manage est root sur l'hôte. Les versions intermédiaires ont ajouté IPv6, la vérification des digests de couches et des paquets apt et rpm pour Debian 13+, Ubuntu 24.04+ et Fedora 44+.

Pourquoi c'est important

Piste intéressante pour l'auto-hébergement sans démon Docker, notamment pour des runners GitLab. Le modèle de sécurité équivaut à celui du groupe docker : n'accordez org.nspawn.manage qu'à des comptes de confiance. Projet jeune, à tester hors production.

Lima v2.3 : pilote HCS natif sur Windows, réseau lima-privileged-net sur Linux, TUI

Lima, projet CNCF en incubation, a publié le 6 novembre la version 2.3. Sous Windows, le nouveau pilote expérimental hcs utilise l'API Host Compute System, base de WSL2, sans QEMU. Limites actuelles : mode plain uniquement, ni montages de fichiers ni redirection de ports dynamique, une seule instance HCS à la fois, et DNS à préciser avec --dns. Sur Linux, lima-privileged-net, un assistant privilégié, crée un pont par réseau, lance dnsmasq pour DHCP et DNS, gère NAT et un périphérique tap par instance. Cela rend disponibles les réseaux lima: shared, host et bridged, jusque-là réservés à macOS. Une configuration sudoers unique est requise via limactl sudoers. Sur macOS, un périphérique bloc peut être attaché aux invités VZ. Une interface terminal est ajoutée.

Pourquoi c'est important

Utile si vous utilisez Lima pour des VM de dev ou de test : les VM Linux peuvent enfin avoir une IP joignable depuis l'hôte. L'installation demande des règles sudoers et un binaire appartenant à root, à relire avant déploiement.

NVIDIA Kubernetes Engine (NVKE) : un plan de gestion Kubernetes pour GPU bare metal

Un dépôt apparu dans les tendances GitHub présente NVIDIA Kubernetes Engine (NVKE), décrit comme un plan de gestion pour Kubernetes GPU sur bare metal. Il permet d'exploiter un service Kubernetes managé sur sa propre infrastructure GPU NVIDIA. Les équipes plateforme installent ce plan de gestion pour créer et exploiter des clusters destinés à leurs clients. Chaque cluster de charge de travail a son propre plan de contrôle Kubernetes, son etcd et ses pools de nœuds. Seul un extrait est disponible, donc maturité, licence et prérequis restent à vérifier dans la documentation.

Pourquoi c'est important

Pour les équipes qui louent ou partagent des GPU en interne, le modèle un plan de contrôle et un etcd par cluster va dans le sens de l'isolation forte entre locataires. À suivre, sans conclusion avant d'avoir lu la documentation.

GitHub : timeouts liés à un afflux d'utilisateurs anonymes, nouvel incident le 9 novembre

GitHub Status a ouvert le 9 novembre à 05h59 UTC un incident intitulé « Increased timeouts due to surge in anonymous users » : l'équipe enquête sur des performances dégradées de certains services. La veille, le 8 novembre, un incident proche (augmentation des timeouts pour certains utilisateurs non authentifiés) avait touché les requêtes d'API. Il a été atténué vers 11h50 à 12h29 UTC, puis déclaré résolu à 12h32 UTC. GitHub annonce qu'une analyse détaillée des causes sera publiée dès qu'elle sera disponible. Les extraits fournis ne donnent pas la cause du nouvel incident ni son périmètre précis.

Pourquoi c'est important

Si vos pipelines clonent, téléchargent des artefacts ou appellent l'API GitHub sans authentification, ils sont les premiers exposés. Authentifiez ces appels avec un jeton, prévoyez des retries avec backoff et un miroir ou un cache pour les dépendances critiques.

Kyverno : CVE-2026-124440 (CVSS 9.9), élévation de privilège via apiCall vers cluster admin

Une vulnérabilité critique, CVE-2026-124440 (CVSS 9.9), a été publiée dans la NVD pour Kyverno. Elle touche les versions de la 1.19.1 jusqu'à la 1.19.2 exclue. Le défaut se situe dans la restriction de namespace (« namespace clamp ») de apiCall. En ajoutant des séquences de pourcentage mal formées à urlPath, un locataire d'un namespace peut émettre des requêtes d'API vers d'autres namespaces ou à l'échelle du cluster. Un attaquant peut créer des Policies namespacées dont l'apiCall s'exécute avec le ServiceAccount de l'admission-controller. Il peut alors lire les ressources d'autres namespaces et créer des mutating webhooks, ce qui mène, selon la description, à un accès cluster admin. La description publiée est tronquée. Le correctif est la version 1.19.2.

Pourquoi c'est important

Si vous exploitez Kyverno 1.19.1 dans un cluster multi-tenant où des équipes peuvent créer des Policies namespacées, le risque est direct. Mettez à jour vers 1.19.2. En attendant, vérifiez qui a le droit de créer des Policies et auditez les mutating webhooks récents.

Linux : la mitigation BHI n'était pas appliquée sur certains noyaux compilés sans KVM

Le correctif x86 de la semaine, envoyé avant Linux 7.4-rc2, corrige la sélection de la mitigation Branch History Injection (BHI). Le développeur Debian Breno Leitao a constaté que bhi_select_mitigation() n'activait la protection que si CPU_MITIGATE_GUEST_HOST était défini. Sans KVM, ce paramètre est désactivé par défaut. La mitigation était donc coupée, alors que le vecteur user vers kernel l'exige encore. Sur les CPU Intel concernés, ces noyaux perdaient BHI_DIS_S ou la boucle de nettoyage du BHB. Démarrer avec mitigations=auto,no_guest_host produisait le même effet. Le correctif est marqué pour rétroportage vers les noyaux stables pris en charge depuis 2022, date d'introduction de BHI. Le lot corrige aussi la gestion d'AMD RMPOPT.

Pourquoi c'est important

Si vous compilez vos propres noyaux sans KVM, ou utilisez no_guest_host, vous avez pu rouler sans protection BHI. Surveillez les publications de noyaux stables contenant ce correctif et vérifiez l'état dans /sys/devices/system/cpu/vulnerabilities/spectre_v2.

SGS : un pirate revendique 22,7 millions de personnes issues des contrôles techniques français

Selon ZATAZ, le pirate Chimeraz propose à la vente sur un forum une base présentée comme issue des activités françaises du groupe suisse SGS. Il cite Auto Sécurité, Sécuritest et Vérif'Autos. Il annonce environ 259 millions de lignes et 22 688 152 personnes, 3 988 centres, 74,7 millions de contrôles, plus de 9,5 millions de numéros de téléphone distincts et plus de 4 millions d'adresses électroniques distinctes. Les exemples associent identité, coordonnées, véhicule, kilométrage et montant facturé, avec des dates de 2016 à 2025. ZATAZ souligne que cette présentation est celle du vendeur : l'extrait ne démontre ni les systèmes compromis ni les enseignes réellement touchées. Il rappelle aussi que des lignes ne sont pas des individus. Des titres de presse relayés par Cyberattaque.org évoquent aussi Sécuritest (mots de passe et IBAN) et Vérif'Autos (un prestataire), sans détail disponible ici.

Pourquoi c'est important

Si vous avez fait contrôler un véhicule en France, attendez-vous à du phishing très ciblé mentionnant votre contrôle ou une facture. Méfiez-vous des messages citant votre plaque ou votre prestation. Rien n'est confirmé par SGS dans les sources fournies.

Iris Ohyama : accès non autorisé à un cloud tiers, 7,7 millions de personnes potentiellement touchées

Le fabricant japonais Iris Ohyama, exploitant de la boutique Iris Plaza, indique que les données d'environ 7,7 millions de personnes ont pu être exposées après un accès non autorisé à un service cloud externe. Le chiffre englobe jusqu'à 5,8 millions de membres actuels et anciens et 1,9 million de non-membres. Les données possibles : noms, adresses, téléphones, courriels, sexe, dates de naissance et mots de passe, selon les personnes. Les mots de passe des membres actifs sont stockés chiffrés, sans précision sur le procédé. L'entreprise affirme que les cartes bancaires n'étaient pas dans ce service. Les boutiques ont été suspendues le 28 octobre. L'autorité japonaise de protection des données et la police ont été informées le 29 octobre. Au 5 novembre, aucun usage frauduleux n'était signalé. L'entreprise dit ne pas avoir été contactée par l'attaquant.

Pourquoi c'est important

Cas typique de risque lié à un prestataire cloud : l'incident vient d'un service externe, pas du système principal. Auditez les accès et les secrets de vos services SaaS ou cloud tiers contenant des données clients, et appliquez la même rigueur de MFA et de journalisation.
